and live provider calls. Every number below was measured, not estimated; the
query or script that produced it is named.

Branch audited: `v2/part11-local-inference` (269 tests passing). The audit
itself changed nothing; fixes were applied afterwards on `fv2` and are marked
**Fixed** in the table below. **No live database row has been modified** —

## The triggering question: was recency to blame?

**Hypothesis.** A backfill scored 171 previously-unjudged jobs and only 4
matched (2.3%), against a historical 57/475 (12%). Suspected cause: `recency`
feeds the score twice — once directly at 0.10, once through `success_prob` at
`0.30 × 0.40` — so it carries 0.22 of the final score, and the 0.30→1.00 band
spread costs 0.154.

**The arithmetic is correct.** `0.30 × 0.40 + 0.10 = 0.22`; the band spread is
worth `0.154` of final score.

**The causal claim is refuted.** Recency was reconstructed per row from
`all_jobs.posted_at` against the configured bands, and the score decomposed as
`final − 0.22·recency`:

| cohort | n | avg recency | avg final | recency-neutral | match rate |
|--------|---|-------------|-----------|-----------------|------------|
| 2026-08-08 live | 50 | 0.302 | 0.387 | **0.3205** | 13.8% |
| 2026-08-09 backfill | 140 | 0.300 | 0.337 | **0.2712** | 2.8% |

The 08-08 live run sat at the same recency floor and still matched 5× better.
Recency was already floored before the backfill ran, so it cannot be what
changed. The gap is in `fit`.

Recency *is* a genuine problem — see issue 2 — but it depresses every cohort
equally rather than singling out the backfill.

## Issue 1 — Optional list fields let the local model return `[]`

**Severity: Critical. This is the cause of the 2.3% match rate.**

### Mechanism

`src/llm/schemas.py` declares the three extraction fields with
`default_factory=list`, so Pydantic emits them as **optional, with no
`minItems`**:

```
required: ['role_summary', 'role_category', 'role_level', 'years_required']

required_skills  -> {"items": {"type": "string"}, "type": "array"}
nice_to_have     -> {"items": {"type": "string"}, "type": "array"}
responsibilities -> {"items": {"type": "string"}, "type": "array"}
```

`_complete_native_ollama` passes that schema straight to Ollama as `format`,
which compiles it into a decoding grammar. An empty array is always
grammar-valid, so a 7B model takes the cheap path.

### Evidence

Five runs each over five real JDs, via `_complete_with("ollama", ...)`:

```
DevOps & Data Pipeline Engineer   req_skills: [0, 10,  0,  0, 0]
Database Engineer                 req_skills: [0,  0, 25,  0, 0]
Lead Data Engineer                req_skills: [0, 10,  0, 10, 0]
Project Leader                    req_skills: [6,  0,  0,  0, 0]
Data analytics engineer           req_skills: [0,  0,  0,  0, 0]
```

**19 of 25 empty (76%), and nondeterministic** — the same JD flips between 0
and 25 skills across runs.

The internal control is clean: the four fields that *are* in `required` came
back populated in 100% of runs. Only the three optional ones collapse.

Grounding is exonerated — the raw count is 0 *before* `grounded_skills` runs,
so the model is returning nothing rather than the filter deleting it.

Side-by-side against Groq on the same six JDs: ollama returned
`required_skills=[]` on 5 of 6; groq populated 4 of 6 with real skill tokens
(`Python`, `SQL`, `Spark`, `Kafka`, `Databricks`). Where ollama *did* populate,
it emitted whole requirement sentences rather than skill tokens.

### Why it destroys the score

Empty `required_skills` + `nice_to_have` means `build_jd_context` produces an
empty `jd_skill_vecs`. `select_skill_candidates` then scores every pool skill
at 0.0, so `avg_skill_pool_match` contributes nothing and `fit` loses its full
0.30 weight — **0.165 of the final score**, more than the entire recency
spread this audit set out to investigate.

### Cost in stored data

| cohort | LOW_SCORE rows | zero skills extracted |
|--------|----------------|-----------------------|
| 2026-06-11 | 109 | 1 (0.9%) |
| 2026-06-24 | 43 | 0 |
| 2026-07-01 | 71 | 1 (1.4%) |
| 2026-08-08 | 50 | 5 (10%) |
| **2026-08-09 (backfill)** | **140** | **116 (83%)** |

Across the whole DB: 152 of 695 parsed jobs have no skills at all.

Field-level collapse in the backfill cohort versus the previous run:

| cohort | avg req_skills | avg nice_to_have | avg responsibilities | avg summary chars |
|--------|----------------|------------------|----------------------|-------------------|
| 2026-08-08 | 8.52 | 3.56 | 7.22 | 268 |
| 2026-08-09 | **0.99** | **0.17** | **0.44** | **51** |

### Why the tests did not catch it

269 tests pass. `[]` is schema-valid, so the earlier "5/5 valid" measurement
was accurate — it measured schema conformance, not extraction. Same failure
shape as the config-key typo that killed Telegram and the `"billing"`
substring that abandoned live runs.

### Root cause, after further testing

The first diagnosis above ("the model returns `[]`") was **incomplete**, and
the `minItems` fix it suggested was treating a symptom. Follow-up experiments:

**The keys are absent, not empty.** Capturing the raw JSON rather than the
parsed model shows the model omits the keys entirely; Pydantic's
`default_factory=list` then manufactures the `[]` downstream.

**Context truncation is refuted.** JDs go to ollama unclipped, so overflow of
Ollama's 4096 default `num_ctx` was a live hypothesis. Measured
`prompt_eval_count` peaks at **2301 tokens** across JDs from 1 117 to 10 003
chars, with no length correlation.

**Three compounding causes, separated by ablation** (12 JDs × 2 runs each):

| condition | empty | median words/skill | grounded |
|---|---|---|---|
| A baseline | 71% | 3.0 | 87% |
| B prompt fix only | 62% | 2.0 | 96% |

The prompt fix barely moves the empty rate but sharply improves quality. So
the schema controls *whether* fields appear; the prompt controls *how good*
they are. Both are needed:

1. **Schema optionality** — `default_factory=list` keeps all three out of
   `required`, so the grammar lets the model skip the key.
2. **The system prompt licensed it** — *"When a field is not stated, return
   null (or an empty list)."*
3. **The user prompt never asked for them** — explicit instructions existed
   for every scalar field and for none of these three.

**The transport was also wrong.** `_complete_native_ollama` justified itself
with *"the /v1 shim ignores `response_format`"*. Re-measured against Ollama
0.32.6: **/v1 honours `response_format: json_schema`**, respecting `required`
and `minItems`. That note was stale.

This matters because Instructor's JSON_SCHEMA mode *also states the schema in
the prompt*, so the model is told the fields exist rather than left to infer
it from a grammar. Routing ollama through Instructor on the shared OpenAI
transport — no schema patching at all — gave **5/5 populated** on the same JDs
the native path emptied.

### Fix applied

Instructor + `Mode.JSON_SCHEMA` on the shared transport, the bespoke httpx
client deleted, and the prompt rewritten to name the three fields and demand
exhaustive extraction.

Verified through the real `src.parser.parse()` path on 12 real JDs spanning
1 982–9 791 chars:

```
n=12  empty=0/12 (0%)  median_req=14.5  mean_req=15.2
      median_words/skill=2.0  median_resp=10.0
```

**71% empty → 0% empty**, with skills arriving as short verbatim tokens rather
than sentences.

### Earlier proposed fix (superseded)

Add the three fields to `required` and set `minItems` (1 for
`required_skills` and `responsibilities`; `nice_to_have` may legitimately be
empty).

Measured effect — 3 runs each over the same 5 JDs:

```
baseline            required+minItems
[10,  0,  0]        [10, 10, 10]
[ 0,  0,  0]        [28, 24, 26]
[10,  0, 11]        [10, 11, 13]
[ 0,  7,  0]        [ 7,  6,  4]
[ 0,  0,  0]        [ 3,  3,  3]
```

Empty rate **67% → 0%**, and output is stable across runs. Mean final-score
gain over 20 real backfill jobs: **+0.054**.

Open design question: whether to enforce this only on the constrained local
path or in the shared schema. A shared `minItems` makes an empty list a
validation failure for hosted providers too, which costs a retry on JDs that
genuinely list no skills.

## Issue 2 — LinkedIn never supplies `posted_at`

**Severity: High.**

```
site      | rows | with posted_at
----------+------+---------------
linkedin  |  472 |   1  (0.2%)
indeed    |  273 | 273  (100%)
```

Verified live, not just historically: a fresh JobSpy scrape with
`linkedin_fetch_description: true` returned `date_posted=None` for 8 of 8. The
mapping at `src/scraper/jobspy_wrapper.py:117` is correct — JobSpy has nothing
to give.

Every LinkedIn job therefore falls through to `recency_score.default` (0.30).
But `scraper.hours_old` is 24, which *guarantees* the posting is under 24h old
— a value the config's own bands price at **0.60**. Every LinkedIn job is
charged `0.22 × 0.30 = 0.066` it does not owe.

LinkedIn is currently the only enabled source, so recency is not a signal at
all right now — it is a constant tax on every job.

**Cost:** of 284 rejected LinkedIn jobs, **62 would cross 0.50** at recency
0.60. Indeed jobs are unaffected (0).

**Do not fall back to `scraped_at`.** Tested: it drives `hours ≈ 0` → recency
1.00 → 20/20 matches on a sample where the stored verdict was 0/20. That is
saturation, not accuracy. The defensible treatment is "unknown → 0.60",
matching the window the scraper already guarantees.

**Combined with issue 1**, on 20 real backfill jobs: stored **0/20** →
**7/20**.

## Issue 3 — `not_applied` records no scores

**Severity: High (diagnostic capability).**

All 693 `not_applied` rows have `fit_score`, `success_prob`, `recency_score`
and `final_score` NULL. The columns exist; `_write_not_applied`
(`src/main.py:492`) merges only `job_id`, `reason_category`, `reason_detail`
and `not_applied_at`, discarding the `SelectionResult` entirely. Same omission
in `src/cli/backfill.py`.

The entire rejected population — the population you need in order to ask "why
did nothing match?" — is score-blind.

This audit was only possible because the LOW_SCORE path happens to stringify
the score into `reason_detail`
(`reason_detail=str(result.final_score)`), letting the final score be
recovered with a regex cast. Every component score had to be reconstructed or
recomputed. One refactor of that line and the question becomes unanswerable.

## Issue 4 — Cooldown and location rejections are never persisted

**Severity: Medium.**

Reason breakdown across all 693 rows:

```
LOW_SCORE            420
HARD_FILTER_LAYER_3  123
DUPLICATE             97
ROLE_MISMATCH         22
PARSE_FAILURE         15
NEAR_DUPLICATE        14
BUILD_FAILURE          2
```

**Zero `COMPANY_COOLDOWN` and zero `LOCATION_DISALLOWED` rows**, despite 51
companies sitting in `company_cooldown`.

Cause: `_write_not_applied` skips any job not already present in `all_jobs`
(a deliberate guard — the FK would abort the commit). But cooldown and
location are decided in the pre-filter loop, *before* `session.add_all(passing)`
inserts anything. Those rejections therefore leave no `all_jobs` row and no
`not_applied` row. They vanish with only a log line.

`DUPLICATE` rows exist only because those jobs were already in `all_jobs` from
an earlier run.

Consequence: there is no way to measure what the 10-day company cooldown or
the Delhi-NCR exclusion actually cost.

The empty-JD path (`src/main.py:196`) is a similar silent drop, though that
one is deliberate and self-healing — the job is re-scraped next run.

## Issue 5 — 8 of 15 NEAR_DUPLICATEs are false positives

**Severity: Medium.**

The 14 NEAR_DUPLICATE verdicts (15 linked rows) were judged on the old
truncated embeddings, which compared only JD openings — i.e. company
boilerplate. Recomputed against the corrected whole-document vectors:

```
cosine_now | same_company | same_role
-----------+--------------+----------
0.8297     | True         | False   <- false positive
0.8508     | True         | False   <- false positive
0.9215     | True         | False   <- false positive
0.9217     | True         | False   <- false positive
0.9333     | True         | False   <- false positive  (x3)
0.9612     | True         | False
0.9924     | True         | True
0.9927     | True         | True
0.9983     | True         | False
1.0000     | True         | True    (x4)
```

**8 fall below the 0.95 threshold**, every one of them `same_role = False` —
different roles at the same company, matched on shared boilerplate. The 7 at
≥ 0.9612 are genuine reposts.

Those 8 jobs were suppressed without ever being scored and should be
re-judged.

## Issue 6 — 11 jobs hold contradictory verdicts

**Severity: Low.**

11 `job_id`s appear in **both** `applied` and `not_applied`, all with reason
`DUPLICATE`, all dated the same day as their `built_at` (5 on 2026-07-01, 6 on
2026-08-08). Each was notified and simultaneously recorded as a rejected
duplicate.

Not yet root-caused. Most likely the same `job_id` arriving twice within one
run from two different search terms, with `existing_ids` computed once at
batch start.

## Issue 7 — `role_level` disagrees between providers

**Severity: Low / watch.**

On 6 shared JDs, ollama and groq disagreed on `role_level` twice
(mid↔senior, lead↔senior). With seniority weights of junior 1.00, mid 0.80,
senior 0.40, lead 0.15, a single mid↔lead disagreement swings `success_prob`
by 0.39 — **0.117 of final score**.

The disagreements ran in both directions, so this is noise rather than bias.
Worth tracking once issue 1 is fixed, since a smaller model's level call is
now load-bearing.

## Issue 8 — JD clipping (accepted, already characterised)

45.9% of JDs exceed the 4500-char hosted budget (n=745, mean 4459, median
4258, p95 8350, max 16100). Head+tail retention drops the middle, where
requirement lists usually sit.

This matches the measurement table already recorded in `config/config.yaml`
under `jd_text_default` (3000+1500 → 45% clipped, 88% years, 97% level).

Second-order in practice: clipped Groq still outscored unclipped ollama on 10
real jobs (mean final **0.400 vs 0.364**, groq higher on 7 of 10). Not worth
acting on until issue 1 is fixed.

## Confirmed healthy

- **`existing_job_ids` fix holds.** All 745 jobs now carry a verdict; 0
  unjudged. The change from "present in `all_jobs`" to "present in `applied`"
  did what it was meant to.
- **Whole-document embeddings.** All 739 stored vectors rewritten; the
  near-duplicate recomputation above ran cleanly against them.
- **Test suite.** 269 passing, ~12s.

## Recommended fix order

1. **Issue 1** — `required` + `minItems` in `src/llm/schemas.py`. Largest
   measured gain, and it is what makes local inference viable at all.
2. **Issue 2** — treat missing `posted_at` as "inside the scrape window"
   (0.60), never as `scraped_at`.
3. **Issue 3 + 4** — populate the score columns; write cooldown and location
   rows (insert the `all_jobs` row first, or relax the presence guard).
4. **Issue 5** — re-judge the 8 false-positive near-duplicates.
5. Re-run the backfill against the fixed schema. **Requires explicit
   approval** — it rewrites verdicts on live rows.

Issues 6 and 7 need root-cause work before a fix is worth proposing.
