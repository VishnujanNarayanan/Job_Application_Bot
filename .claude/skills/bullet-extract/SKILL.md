## Scope: one repo in, one extract out

This skill writes **one file**: `bullet_extract_latest.yaml` in the current repo, rotating the previous one to an archive. It does **not** create, edit or rebuild `master_profile.yaml`, and it doesn't touch any other repo.

The master profile is assembled **later**, by the operator, once every repo has been extracted. That's done with `python tools/build_master_profile.py` in job_application_bot. The tool reads each repo's `bullet_extract_latest.yaml`, carries `personal`/`education`/`certifications` and work dates forward, prefers `demo` over `link`, unions `skills_pool` / `gap_skills`, validates against `MasterProfile`, and checks every bullet byte for byte against its extract. **Since 2026-10-08 the profile is hand-maintained**, so a new extract joins it through `--keep` or by hand, never a full rebuild (Step 11).

So the extract must be something that tool can read:
- **Entry fields:** `id`, plus `name` / `link` / `demo` / `tags` for projects, or `company` / `actual_title` / `safe_title_aliases` / dates / `employment_type` for work.
- **Block keys it copies:** `role`, `role_fit`, `entry_header`, `entry_dates`, `project_line`, `checklist`, `checklist_source`, `market`, `target_titles`, `title_aliases`, `bullets`, `extra_bullets`, `covered`, `missing`, `titles_dropped`, `lead_pct`.

At the end of the report, remind the user to run the builder after the remaining repos are extracted. Never run it yourself.

## How the bot uses this file (read before writing a single bullet)

Everything below the rules follows from these facts about Layer 4:

1. **Each entry renders under ONE lead block.** For every JD the bot picks the lead block by what its **`bullets:` alone** cover of that JD's keywords (75%) plus cosine similarity (25%). Extras never count toward winning the lead. → **Main bullets must be keyword-dense, or the block never leads.**
2. **The render set is the lead block's `bullets:` only.** The main bullets of every other block in the entry are **unreachable** for that JD.
3. **`bullets[0]` is pinned as the summary.** It always renders first, and its keywords count as covered.
4. **Zero-repeat rule.** A bullet that restates **any** keyword already covered in the entry, the pinned summary included, is **never selected**. There's no penalty and no trade-off; it simply can't render.
   - In `bullets:`, a keyword used twice means the second bullet is dead whenever the JD names that keyword.
   - In `extra_bullets:`, a single already-covered keyword bars the **whole** extra, and any other skill it carried is lost with it.
5. **`extra_bullets` pool across EVERY block of the entry.** When the JD asks for something the lead block's main bullets don't say, the bot looks in all blocks' extras. An extra from a less related block still counts, just ranked lower (relevance scaling, floor 0.05).
6. **Caps:** a project renders at most **5** bullets, work at most **8**, minimum **3**. Phase 1 fills from JD keywords. Phase 2 fills remaining slots with **canonical tokens from the lead block's `checklist`** titles. Both stop at zero gain.
7. **Gated terms.** Bullets naming `Claude Code, OpenAI Codex, Codex, Cursor, GitHub Copilot, Copilot, Model Context Protocol, MCP` are removed unless the advert names one, and render at most once per page.
8. **Across entries**, a keyword may render in at most 2 entries (`max_keyword_renders`). Repeating across entries is otherwise fine.
9. **Title aliases** are embedded and are the titles an entry may render under. For work entries, `safe_title_aliases` must contain `actual_title` plus the union of every block's aliases (hard rule #6).

So the shape is:

> **Thick main bullets per block, each keyword said once.** Then a **large pool of thin extras** across the entry: one skill each, so any skill the repo proves can be recovered whichever block leads.

## Step 0 — Read the guide first

**0.1** Read `video_qualification_method.md`, `resume_method.md` and `score_coverage.py` in full.

**0.2** Run `grep -n '^### ' job_qualifications.md` and read the rows for every role this repo could plausibly support. Untiered lines are the **required** set that coverage is scored on. Lines starting `Rare:`, `Bonus:`, `Nice to Have:` or `Extra Credit:` are differentiators, but JDs ask for them too, so give them extras.

**0.3** Choose the checklist, one or two titles per block. It sets the scoring denominator **and** phase-2 fill (fact 6).
- Use the **geography row** for the market (Python Dev (India), EU - Full stack, ...). **Never union across markets.**
- **Variants of one title may be unioned.** `DevOps Engineer (variant 1)` + `(variant 2)` are one job described by two recruiters. Write the exact `(variant N)` heading, or the bare title to take all its variants.
- Two differently named titles may be unioned only when they're **the same job renamed** (e.g. Data Engineer + Analytics Engineer). Add a comment saying so.

## Step 1 — Identity

Run `ls -la`, `git remote -v` and `git log --oneline | head -30`.

If a previous `bullet_extract_latest.yaml` exists, reuse its identity labels without interviewing the user. Otherwise ask:
- **Project:** `id` slug, `name`, `link`. Prefer a live demo, else the repo.
- **Work:** `id`, `company`, `actual_title`, `start_date` / `end_date` (`YYYY-MM` or `present`), `employment_type` (`employment` or `freelance`), optional `location` and `link`.

## Step 2 — Investigate. Evidence, not assumption.

- Read `README`, dependency files, the source tree, `config/`, CI, `Dockerfile`, compose files.
- Count tests (`grep -rc 'def test_'`) and read core-module docstrings plus `wc -l`.
- **History:**
  - `git log --diff-filter=D --name-only` to list deleted files
  - `git log -p --follow -- requirements.txt` to see dependencies that were added and later removed
  - `git log -S"<tech>"` for every technology you might claim
  - `git show <sha>:<path> | wc -l` to catch stubs

A one-line stub is **not experience**; it goes in `gap_skills`. A real integration that was later removed can become an extra with `# evidence: removed in vN; was <path> at <sha>`.

**Build a skills inventory as you go:** every technology, practice and domain term with evidence. It becomes `skills_pool` (Step 10), and **each item needs an extra** (Step 5B).

## Step 3 — `_meta`

```yaml
_meta:
  what_it_does: >-      # 2-3 plain sentences a layman understands
  industry: "..."
  open_questions: ["[VERIFY: ...]"]      # only the user can answer these
  roles_not_supported:
    - {role: quant, reason: "a concrete absence, e.g. no market data"}
```

## Step 4 — Entry and role blocks

Role names: `backend, data, ml, devops, fullstack, quant, finance_market`. Others (e.g. `sdet`) are allowed; the bot types `role` as a free `str`. Write one block per role the repo genuinely supports, and give each block a **distinct focus**, so the lead-block choice means something.

```yaml
projects:                       # or work_experience:
  - id: "slug"
    name: "Display Name"        # work: company, actual_title, start_date, end_date,
    link: "https://..."         #       employment_type, safe_title_aliases (fact 9)
    tags: [<every role below>]
    role_blocks:
      - role: backend
        role_fit: primary       # primary | adjacent (adjacent loses exact ties)
        entry_header: "Display Name"
        # entry_dates: "Jan 2025 - Present"   # WORK ONLY; projects must not have it
        project_line: "Project: <plain description>"   # the WHERE
        checklist: ["<exact sheet title>"]
        market: "India"
        target_titles: []       # 8b only
        title_aliases: [...]    # 8d, 10-25
        bullets: [...]          # 5A, render set
        extra_bullets: [...]    # 5B, recovery pool
        covered: []             # 8a, written by script
        missing: []             # 8a, written by script
        titles_dropped: []      # 8b
        lead_pct: 0             # 8a, written by script
```

- Bullet ids: `{slug}_{role}_b{n}` for bullets and `{slug}_{role}_x{n}` for extras, unique across the file.
- Each bullet is `id`, `text`, and a `# evidence:` comment (files, commits, counts).

## Step 5 — Writing bullets

### Rules for every bullet

| # | Rule |
|---|---|
| R1 | **WHAT + HOW + WHY.** The WHY is a plain business reason that **names who benefits**. Not a brag, and not vague. Find it with the **so-what ladder** (5C). |
| R2 | **Literal tokens.** Write the checklist's exact words. Write the specific tool *and* the generic token (Postgres → also SQL). Separate keywords with commas; never let one modify another. Name the cloud. Expand acronyms: `Long Form (LF)`. |
| R5 | **Shape: fill whole lines.** Main bullets 148–172 characters (two full lines); `b0` 240–262 characters (three full lines); a bullet packed with long keyword phrases stays at about 162. 35 words or fewer, exactly one period, past tense. Extras keep 28 words or fewer until their line rule is settled (bot issues #138, #143). See 5D. |
| R7 | **No hot dogs** (impressive detail that isn't on the checklist) and **no ketchup** (trailing technical clauses). |
| R8 | **Banned words:** leverage, spearhead, synergy, robust, seamless, cutting-edge, state-of-the-art, world-class, passionate, dynamic, results-driven, team player, responsible for, helped, helping, worked on, various, utilize, facilitate, best-in-class, successfully, in order to, ninja, rockstar, owned, shipped, drove, scalable, holistic. |
| R9 | **Real figures only.** No invented or code-level numbers (test counts, line counts, latency you never measured). A **real business figure is the strongest proof you have**: money saved (a vendor bill per quarter), hours saved, people served (members, users), growth (client acquisition up by a measured share), time to launch, funding it supported (a seed round). Put it in `b0` where it exists. A figure never replaces the WHY; it sits beside it. Digits are otherwise only inside technology names (S3, boto3, Jinja2). |
| R10 | **Evidence or nothing.** Anything read about or stubbed goes in `gap_skills`. A claim must survive an interview question: scoped or designed work says "Designed" or "Planned", never "Built" or "Ran". |

### 5A. Main bullets (`bullets:`) — keyword maxing

- **Keyword maxing:** each bullet carries **4–6 keywords** (minimum 3), comma-listed. **Checklist tokens first**, in the checklist's literal wording (e.g. "Database testing/SQL", "monitoring and logging", "CI/CD pipelines"), then real technology names a JD for this role would ask for.
- **The checklist sets the length.** A block has only 10–15 checklist tokens it can honestly claim, and each is spent once. So the number of main bullets is roughly *honest tokens ÷ 3–4*, usually 3 to 6. Don't pad with a thin main bullet; put that material in extras.
- **Every keyword appears ONCE across the block's `bullets:`, `b0` included** (fact 4). Before writing each bullet, list what `b0` and the earlier bullets already say, and use only new keywords. Watch for incidental repeats: a second "Python", "SQL", "AWS" or "cloud" kills the bullet.
- **`b0` is the summary** (fact 3): one plain sentence an outsider follows, carrying the block's **core stack tokens** (the language plus the role's must-haves), because nothing may be implied (R3 in the guide).
- **One process bullet** per block is cheap coverage: Git, CI/CD, Agile, SDLC, testing.
- **Unique opening verb** per block. Repeat the role's own name somewhere in the block (e.g. DevOps).
- **How many:** at least 3 (the bot's floor).
  - Projects: up to **5–6** if the tokens allow; the cap is 5.
  - Work: up to **6–8**.
  - Across the block, aim to hit **75% of the checklist** (that's the measured `lead_pct`).
- A block's main bullets must all be about **this** role's kind of work. The lead is partly chosen by cosine similarity, and hot dogs dilute it.
- **Never put a gated term (fact 7) in a main bullet.**

### 5B. Extra bullets (`extra_bullets:`) — many, thin, single-subject

- **One keyword subject per extra; two only if they're inseparable** ("Docker and Docker Compose", "Alembic migrations"). If any keyword in an extra is already covered, the whole extra is barred, so a second skill in the same sentence is a skill you'll lose.
- **Keep incidental tech out of the HOW and WHY.** Write "on a recurring schedule", not "in Python on a cron". Otherwise the extra is barred on every page that has already said Python.
- **Coverage of the inventory:** write an extra for
  1. **every keyword that appears in any block's main bullets.** Another block may lead, and then those main bullets are unreachable (fact 2).
  2. **every `skills_pool` item**, and every Bonus/Rare/Nice-to-have token the repo can prove.
  3. **the cross-cutting skills** every block needs available: language, SQL, Docker, Git, CI/CD, cloud, testing, Linux.

  In practice that's **20–40+ extras per entry.** That's expected, not bloat: nothing in the pool renders unless a JD asks for it.
- **Each skill once per entry.** Two extras covering the same subject can never both render (the second repeats). Put each extra in the block where it belongs most, because related-block extras rank higher.
- **Gated terms** (Claude Code, Cursor, Copilot, MCP, ...) each go in **their own extra**, alone.
- Extras still obey R1–R10: WHAT + HOW + WHY, one period, 28 words or fewer, no numbers.

### 5C. The WHY: so-what ladder and the plain-impact test

Settled on the bot's profile across issues #74, #75, #135 and #142.

**The so-what ladder.** Write the first WHY that comes to mind, then ask "so what?" of it, three to five times. Keep the **deepest answer that is still true and specific to this work**. Stop one step before it turns generic ("protected the company's reputation", "made money"): a generic WHY fits any bullet and survives no interview question.

> CI/CD bullet. "…stopping broken code" → so what? *no broken collector went live* → so what? *the overnight refresh didn't fail* → so what? **researchers never started the day with missing data**. Stop there.

**The plain-impact test.** The model bullet the user picked:

> Scheduled monthly collector runs with Prefect so a long crawl finished on time, and set Budgets alerts on the cloud bill, warning the owner of rising costs early.

- **Each tool gets a plain consequence** a business cares about: time saved, money saved, a mistake avoided, someone no longer blocked or waiting, something that wasn't possible before. Split the sentence per tool only when it reads naturally.
- **The WHAT reads as an action**, not a pile of nouns. "Moved AWS S3 cloud storage data into SQLite warehouse data models and…" fails; "Loaded … giving analysts one table instead of hundreds of files" passes.
- **Clever-but-unclear fails.** Rejected WHYs: "giving analysts one query for any cross-market question", "letting a team add any company without a new feed", "its API only gives in pieces", "without researchers finding the errors first".
- **No insider nouns in the WHY.** Keywords carry the jargon; the WHY is plain English. Rejected: tick, order flow, backtest, REST endpoints, serve in bulk, crowding, sizing, rows.
- **The WHY may reshape the whole bullet.** Rewrite the WHAT around the better WHY, as long as every keyword, every real figure and the main idea survive.

**Beneficiaries.** Name the real one and vary it across the block: the research team, analysts, traders, the client, the owner, members, users, people seeking legal help. **Never** a visitor, a reviewer, a reader, testers or "anyone": a demo audience is not a business outcome (#75). Don't let one noun ("the desk") become the default; #135 found it in three quarters of one entry's bullets.

**Connectors.** Vary what joins the WHY: so, letting, giving, keeping, sparing, making, ensuring, because, instead of, while. One connector may appear up to three times in a block; past that it reads as one sentence repeated (#135 found "so" in nine of ten bullets). Don't contort a clear sentence just to avoid a third "so".

**Projects keep honest beneficiaries.** Use the intended user of the tool (a fraud analyst, a support team, a law firm) and never invent customers or results.

### 5D. Length: write to the character ranges

Measured by rendering the bot's template (Arial 10.5, Liberation Sans in LibreOffice, a 431.9pt bullet column) on 94 bullets, with every keyword bolded:

| Target | Characters | Why |
|---|---|---|
| Main bullet, 2 full lines | **148–172** | Under ~145 the 2nd line is less than 60% full; above 172 bolded keywords can push it onto a 3rd line, and from 184 every bullet spilled. |
| `b0`, 3 full lines | **240–262** | Under ~238 the 3rd line can be under 60%; 278 went to 4 lines. |
| Keyword-dense bullet | **≤ ~162** | Long bold phrases ("stakeholder management", "Apache Iceberg") break lines early; two 166–167 character bullets spilled. |

Letters are proportional (a line holds ~162 narrow letters but ~66 wide ones; prose averages ~87), so the ranges are for prose like these bullets. Count characters while drafting. When a better WHY makes a bullet too long, cut filler from the WHAT first, then shorten the WHY's wording, and only then stop the ladder one rung earlier. Never cut a keyword.

Example pair: the same skill written as a main bullet and as an extra.

```yaml
bullets:
  - id: "jab_devops_b2"
    text: "Automated builds with GitHub Actions, CI/CD pipelines and Docker images on Linux, so jobseekers got matches without anyone tending a server."
extra_bullets:
  - id: "jab_devops_x7"
    text: "Automated every build with GitHub Actions, so jobseekers never received a resume built from untested code."
```

### 5E. Grouped keyword lines (`keyword_lines:`, entry level, #138)

Every keyword the entry proves must also get a **phrase**, and every phrase joins every **frame** its verb fits. A keyword with no phrase never reaches a grouped line. Full rules: the bot repo's `docs/profile_edits.md` and `master_profile.example.yaml`.

- **Phrase:** `{id, kw, group, source, text}`. The text is a clause with no full stop that names the keyword, true to `source` (a bullet of this entry, main or extra). Never claim more than the source does ("weighed Airflow").
- **Frames first, and as large as honesty allows.** `{id, text with {kws}, ending, allowed}`: one group's keywords with commas, e.g. "collected the market data with {kws}" holding every scraping and collection tool. Complementary tools and substitutes alike, as long as the verb is true for every member. A phrase may sit in several frames.
- **Ending, one per frame:** a plain business WHY, true for every member, sharing no 4-word run with any bullet of the entry (the loader rejects it).
- **skip:** terms the bullets match that are not the skill (wrong sense, domain word, combined spelling), each with a comment saying why.
- **Check:** `python -m tools.keyword_lines_check <entry_id>` in the bot repo must report 0 missing. Reparse and the assets push refuse a profile with gaps.
- A re-extract keeps the entry's existing `keyword_lines` (build_master_profile carries them). After adding or changing bullets, run the check and phrase every new keyword.

## Step 7 — Measure, then improve

```bash
python3 "$GUIDE/score_coverage.py" --per-title
```

This scores `bullets:` only, which is what renders. Improve **only with true material**:
- reword a bullet to the checklist's literal phrasing
- add a keyword the block hasn't said yet to a thin bullet
- swap a restating bullet for a new one

Re-run after every change. **Never type a coverage number.**

## Step 8 — Results

**8a.** Run `python3 "$GUIDE/writeback_coverage.py"`. It writes `covered`, `missing` and `lead_pct` into each block by key and then verifies them against the grader. **Never write these by hand or with string replace.** A previous run's replace shifted every block's lists by one.

**8b. target_titles.** A title enters only if **its own per-title figure is ≥ 75%** (`EARNED`); never judge on the merged pool. Every other checklist title goes to `titles_dropped` with a reason naming the real missing skills. An empty `target_titles` is an honest result.

**8c.** `lead_pct` is the script's merged figure.

**8d. title_aliases — aim for 10–25 per block.** They're the titles the entry can render under and the role embedding the bot matches against.
- Run `python3 "$GUIDE/suggest_titles.py"`. It applies the gate (the title's own name words must appear in the bullets), ranks by IDF, and labels titles `alias` or `weak`. Keep `alias` sheet titles from the same role family, commented `# near-miss sheet title`.
- Add the market's common titles: plain, Junior, Associate, and stack-qualified forms (Python Developer, Backend Engineer, Junior Python Developer, API Developer, ...).
- If the gate rejects a title the repo **genuinely** supports, add the literal word to a bullet, backed by evidence. Otherwise remove the title.
- **Work entries:** set `safe_title_aliases` to `actual_title` plus the union of all block aliases.

## Step 9 — Lint

```bash
python3 "$GUIDE/lint_extract.py"
```

Fix every ERROR and review every warning. It checks:
- main bullets have ≥ 3 checklist keywords (aim 4–6)
- **no keyword repeats within a block's render set**
- extras have ≤ 2 keyword subjects
- **every keyword claimed in any render set has an extra**
- gated terms appear only in solo extras
- no duplicate-subject extras
- `skills_pool` items appear in some bullet
- words, one period, banned words, numbers, opening verbs, ids
- alias counts, work `safe_title_aliases`, entry dates

After fixes, re-run Step 7 and 8a.

## Step 11 — Report to the user

1. **File:** name, which archive the old one was rotated to, legacy files untouched, blocks, main bullet count, extras count.
2. **Coverage table, measured:** block | lead_pct | change vs previous run | per-title figures. Say whether any title reached 75%.
3. **Lint result:** 0 errors, plus any warnings you chose to keep, and why.
4. **Real skill gaps**, as a learning list in priority order, with the titles each blocks.
5. **Sheet noise to ignore:** multi-word tokens no sentence can carry literally.
6. **[VERIFY] items**, and flags (history findings, consumer compatibility, missing guide files).
7. **Next step (the operator's, not this skill's):** `master_profile.yaml` has been hand-maintained since 2026-10-08. Every bullet in it was rewritten by hand (#74, #135, #142), and the per-repo extracts are stale history. **A full rebuild with `tools/build_master_profile.py` would revert all of that.** Add the new entry with the builder's `--keep` pinning every existing entry, or paste the new entry into `master_profile.yaml` by hand, then load it through `MasterProfile` to validate.
